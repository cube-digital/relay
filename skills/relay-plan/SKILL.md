# Relay plan

Goal: the user’s arguments

Produce a plan. Do not write code.

**Unattended.** HQ launches a plan with `--unattended` at the start of the arguments. In that mode, nobody can answer, and the process ends with your turn. Remove that flag from the goal. Skip step 2. List the defaults that you selected as assumptions in the spec. Dispatch each agent in the foreground and wait for it. If `--flow <name>` comes before the goal, remove it from the goal and use that flow in step 1.

**Business analyst.** The business analyst joins only when the arguments include `--business-docs <path>`. The path is a file or a folder of business documentation in the repository. Remove the flag and its path from the goal. Step 4 passes the path on. The business analyst writes the requirements from that documentation and the source. Without the flag, the CLI skips the requirements pieces.

1. **Understand.** If the goal is empty, ask what to build and stop. If it is a path, read that spec or design and its relevant linked requirements. Preserve decisions already agreed in the conversation. Dispatch scout agents (cheap) for missing file, convention, and test-command evidence. If dispatch is unavailable, inspect only the relevant sources directly. Reuse existing findings. Select the flow, unless `--flow` set it: `bugfix` when the goal is to fix a defect, otherwise `feature`. `relay flow list` shows each flow.
2. **Ask once, briefly.** Ask at most three questions, together, only where the answer changes scope, acceptance behavior, or a risky choice. Do not reopen settled design decisions. For routine reversible details, state sensible assumptions and continue. If a material design decision is unresolved, identify the affected work and resolve that decision before planning dependent tasks; silence is not agreement.
3. **Source.** Use a supplied spec or agreed design as the source. Keep its path, revision when known, decisions, contracts, and acceptance scenarios. Do not compress a design into a replacement one-page spec. If neither was supplied, write `docs/relay/specs/YYYY-MM-DD-<slug>.md`: goal, observable behaviors, out of scope, constraints, and assumptions. Keep this new spec under a page. The slug of the source is also the slug of the plan.
4. **Pieces before the plan.** Run `relay flow at --flow <flow> --slug <slug> plan.before`. Add `--docs <path>` when the arguments gave `--business-docs <path>`. Dispatch each piece that the command lists as its role, under the agent name that it prints, with one line: "Read <brief>; it is your instruction. Write your report to <report>." Wait for each piece. A blocking piece must be DONE before the architect writes the plan.
5. **Plan.** Dispatch the existing architect with the source paths, the flow, the reports from step 4 (such as `docs/relay/requirements/<slug>.md`), settled decisions, builder discretion, and scout findings (paths and one-line notes, not file contents). Instruct it to use its plan responsibility, read `<relay-root>/skills/plan-with-tiers/SKILL.md` and `template.md`, write `docs/relay/plans/YYYY-MM-DD-<slug>.md` with `"slug": "<slug>"` and `"flow": "<flow>"`, run `relay lanes <plan>` until it has no errors, and return the path. If dispatch is unavailable, follow that same procedure in the current conversation.
6. **Check.** Run `relay lanes <plan>`, `relay forecast <plan>` and `relay board <plan>` (it writes the board the run will light up) yourself. If lanes still reports errors, resume the architect with them once. After that fix small issues in the plan directly. Then run `relay flow at <plan> plan.after` and dispatch its pieces as in step 4. For each piece of steps 4 and 6, run `relay flow done <plan> <piece> --status pass|findings|blocked --report <report>`.
7. **Hand over** in this order: the plan path. The flow and the pieces that ran. One line per task (`T3 · mid · high risk · 2 tests — title`). The lanes and waves from `relay lanes` and the forecast, both in code blocks, unchanged. The assumptions. End with the next step: `/relay:run <plan>` to run it here (`/relay:board` then shows its progress), `/relay:marathon <plan> <hours>` when it spans more than one 5h window, or changes in plain words (then update the plan and show lanes and forecast again).
