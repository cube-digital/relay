# The Codex harness, as relay needs to know it

What `@openai/codex` 0.163.0 (the ChatGPT coding harness: CLI, TUI, `exec`, app-server used by the IDE extension and the desktop app) meters, stores and exposes, read from the binary with REA 6.7.0 on 2026-10-22. This is the reference your colleagues asked for: every fact carries how it was established, so nobody has to open the binary again unless the version changes.

Evidence kinds used below: **observed** (REA process capture of the real binary, files under `../evidence/captures/`), **static** (a string in the binary's `.rodata`, file offset given; the full string table with offsets is `../evidence/rodata-strings.radare2-izz.txt.gz`), **documented** (OpenAI's docs, URL given), **community** (unofficial, unverified), **unknown** (not recovered).

Target: `vendor/x86_64-unknown-linux-musl/bin/codex`, SHA-256 `399ff69c431c066e40de318fba45c2b07f45a76b19939d247ee4828fc70c4215`, 296,865,480 bytes, ELF64 static-pie, stripped, rustc 1.95.0 (2026-04-14). No cargo-auditable section (`.dep-v0` absent), so dependency recovery was not available; `.rodata` is 15,048,396 bytes at file offset 0xe4fd000. Tooling note: REA's rizin adapter was run with `REA_RIZIN_COMMAND=radare2` (radare2 5.5.0 from apt; rizin is a radare2 fork and the one-shot profile `-N -q -e scr.color=0 -c` is identical), and the Evidence records name the executable actually used.

## 1. Usage windows and the readings relay routes by

The backend meters subscriptions in rolling windows and reports them to the client; the client never computes a percentage itself. A reading is a `RateLimitSnapshot` (static: struct name at 0x0e776da3, field list at 0x0e94db3c): `primary` and `secondary` windows, each `{ used_percent, window_minutes, resets_at }` in the core protocol (static 0x0e778178, 0x0eb212a2) and `{ usedPercent, windowDurationMins, resetsAt }` in the app-server v2 schema (observed: `../evidence/schemas/GetAccountRateLimitsResponse.json`), plus `plan_type`, `limit_id` / `limit_name` (the metered pool, e.g. `codex`), `normal_model_slug` (the model whose display name describes a quota alias), `credits { has_credits, unlimited, balance }`, `spend_control_reached` and `rate_limit_reached_type` (`rate_limit_reached`, `workspace_owner_credits_depleted`, `workspace_member_credits_depleted`, `workspace_owner_usage_limit_reached`, `workspace_member_usage_limit_reached`). The app-server response adds `rateLimitsByLimitId` (a multi-pool view), `rateLimitResetCredits { availableCount, credits[] }`, `ordinaryUsageAllowed` and a backend-owned `rateLimitUpsell` banner. The older `resets_in_seconds` field relay's `parseCodexRateLimits` still accepts no longer exists in this version (0 occurrences in the binary); `resets_at` is a unix timestamp in seconds.

Which windows exist depends on the plan (documented: learn.chatgpt.com/docs/pricing): Plus and Standard Business meter a five-hour window and a weekly one; Pro plans currently have no five-hour limit, so their primary window is the weekly one; Enterprise/Edu with flexible pricing have no fixed limits and run on credits. The status line can show `five-hour-limit` and `weekly-limit` (static 0x0e6d6097), and the analytics feature `analytics_plan_history` previews "five-hour and weekly allowance history for consumer accounts" (observed: `codex features list`). Plan types in the protocol: free, go, plus, pro, prolite, promax, team, self_serve_business_prolite, self_serve_business_usage_based, business, ent26, enterprise_cbp_automation, enterprise_cbp_usage_based, enterprise, edu, edu_plus, edu_pro, unknown.

Where a reading can be obtained, in order of preference:

1. App-server JSON-RPC: `account/rateLimits/read` (full snapshot) and the sparse `account/rateLimits/updated` notification, which the docs say to merge into the last read. Observed: without ChatGPT auth the read fails with `-32600 "codex account authentication required to read rate limits"`. The app-server runs as `codex app-server --listen stdio://` (or `unix://`, `ws://`), and a shared daemon (`codex app-server daemon`, `daemon_auto_start` on by default) serves every client.
2. The session rollout file `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ISO ts>-<thread uuid>.jsonl`: `{"type":"event_msg","payload":{"type":"token_count","info":{total_token_usage,last_token_usage,model_context_window},"rate_limits":{...}}}` (static `TokenCountEvent with 2 elements` 0x0eb212a2; observed rollout layout in `../evidence/captures/rollout-exec-json-sample.jsonl`). This is what `relay budget --codex` reads today; the snake_case field names are confirmed, the file naming is `rollout-<ts>-<uuid>.jsonl` with `_<n>` suffixes for later context windows (static 0x0e55b95a).
3. The backend directly: `GET https://chatgpt.com/backend-api/codex/wham/usage` (static 0x0e5331b4, base URL 0x0e73d508), whose `RateLimitStatusDetails` carries `used_percent, limit_window_seconds, reset_after_seconds` (static 0x0e70990a). Reset credits: `/wham/rate-limit-reset-credits` and `/consume` (static 0x0e5331e9, 0x0e533237).

API-key sessions get no reading at all: the TUI `/status` shows `Limits: data not available yet` and `/usage` says `Sign in with ChatGPT to use /usage` (observed: `../evidence/captures/tui-status2.capture.json`).

The client already nudges on limits: a "rate-limit-switch-prompt … Uses fewer credits for upcoming turns … Approaching rate limits" dialog (static 0x0ec2b902) with the `hide_rate_limit_model_nudge` notice key (static 0x0e779d9b), and memory generation is gated by `memories.min_rate_limit_remaining_percent`, default 25 (documented). (`hide_rate_limit_warning` appears only in a packed field-name table at 0x0e5d51d0.) Both are precedents for relay's 60/85 gates.

## 2. Credits: how tokens are priced

The backend estimates every thread in credits and the client fetches it: `POST /wham/usage/thread-estimates/query` (static 0x0e52fabe) returns `estimated_usage_credits_micros`, `estimated_usage_usd_micros`, `native_usage_usd_micros` and `groups[]` of `{ model, reasoning_effort, speed, net_new_input_tokens, cached_input_tokens, input_tokens, output_tokens, total_tokens, estimated_usage_credits_micros, usage_limit, credit_type }` (static 0x0e705996); the app-server exposes it as `account/usage/read { threadId }` → `threadUsage` (observed schema `GetAccountTokenUsageResponse.json`), next to lifetime and daily token summaries. The TUI status line has `thread-credits` and `estimated-thread-cost` items.

Published credit rates per 1M tokens at Standard speed, input / cached input / output (documented, learn.chatgpt.com/docs/pricing, read 2026-10-22):

| model | input | cached input | output | relative per token at the agent mix |
|---|---|---|---|---|
| gpt-6-astra | 250 | 25 | 1,250 | 100 |
| gpt-6.1-sol | 50 | 2.5 | 250 | 17.6 |
| gpt-6-sol | 50 | 5 | 250 | 20 |
| gpt-6-luna | 2.5 | 0.25 | 12.5 | 1 |

Reasoning tokens are output tokens; there is no separate cache-write charge (documented; the `TokenUsage` struct carries a `cache_write_input_tokens` field, default 0, static 0x0e777c2a). Speed modes multiply usage: Fast 2.5× of included subscription usage (2× on purchased credits), Ultrafast 8× (6×), Ultrafast only on Pro $500 and eligible Enterprise/Edu (documented). The catalog describes Fast as "2x speed, increased usage" on astra and sol 6.1 and "1.5x speed" on sol 6 and luna, whose `default_service_tier` is `priority` (Fast) — observed in `codex debug models`. OpenAI's own ordering check, "local messages per five-hour period" on Plus: Astra 5–45, Sol 6.1 15–160, Sol 6 15–150, Luna 350–3,000 (documented). Community figures (codex.danielvaughan.com, July 2026, unverified) put requests above 272,000 input tokens at 2× input price; the catalog only shows that an extended context exists (`max_context_window` 872,000 against `context_window` 272,000), not its price.

Purchased resets (documented, help.openai.com article 20001507): a purchase restores both the five-hour and the weekly usage immediately, pulls the weekly allowance forward without adding usage, starts a new weekly period at the next request, Plus and Pro personal accounts only, cannot be banked. Earned/banked reset credits exist in the protocol (`RateLimitResetCredit { id, resetType codexRateLimits, status available|redeeming|redeemed, grantedAt, expiresAt, title, description }`, `account/rateLimitResetCredit/consume { idempotencyKey, creditId? } → reset | nothingToReset | noCredit | alreadyRedeemed`); the community reports 30-day expiry.

## 3. Models, context, compaction

The bundled catalog (observed: `codex debug models`, saved as `../evidence/model-catalog.debug-models.json`) lists eleven models; the ones relay routes to:

| slug | context | max context | efforts | default effort | service tiers | multi-agent | tool output cap |
|---|---|---|---|---|---|---|---|
| gpt-6-astra | 272,000 (95% effective = 258,400) | 872,000 | low, medium, high, xhigh, max, ultra | low | priority "Fast, 2x speed, increased usage" | v2, `multi_agent_reasoning_effort` xhigh | 10,000 tokens |
| gpt-6.1-sol | same | same | same | low | same | v2, xhigh | same |
| gpt-6-sol | same | same | same | medium | priority "1.5x speed", default | v2 | same |
| gpt-6-luna | same | same | low … max (no ultra) | medium | priority "1.5x speed", default | v2 | same |

`ultra` is "maximum reasoning with automatic task delegation". `supports_reasoning_effort_updates` is true only for astra and sol 6.1 (effort can change mid-thread). The effective context of 258,400 was observed at runtime in `task_started.model_context_window` of the exec rollout. The catalog has `auto_compact_token_limit: null` for every model, so the auto-compaction threshold is a built-in default computed in code and **was not recovered**; it is configurable through `model_auto_compact_token_limit` with scope `total` (default) or `body_after_prefix`, plus `model_post_turn_compact_threshold_percent`, `compact_prompt` and `experimental_compact_prompt_file` (static 0x0e6c33bf; documented config reference). Compaction is hookable (`PreCompact`, `PostCompact`) and reported as `thread/compacted`. An alternative "token budget" mode (feature `token_budget`, under development, disabled) gives the model `notes`, `history`, `new_context` and `get_context_remaining` ("You have N weighted tokens left in the shared session token budget", static 0x0e540631) with a 6,144-token reminder threshold and a 16,384-token fallback buffer (catalog `model_messages.token_budget`).

The model client records why a response chain could not be continued: `prompt_cache_key_changed`, `model_changed`, `service_tier_changed`, `reasoning_changed`, `tools_changed`, next to `no_previous_response` and `input_mismatch` (static 0x0e8d8b27). Inference, not established by the strings: a mid-thread change of model, effort or speed starts a new chain, and a prompt whose prefix no longer matches is read at the uncached rate, 10–20× the cached one at the published rates.

Model migration notes in the catalog say the newer models "use usage limits further" (Sol 6 vs 5.6: "more efficient so your usage limits go further"; Luna 6: "significantly more efficient"), i.e. per-model multipliers exist server-side and change with releases; the credit rates above are the current ones.

## 4. Subagents

Multi-agent v2 (feature `multi_agent` stable; catalog `multi_agent_version: v2`). Tools and parameters (static 0x0e902eb4–0x0e903200, 0x0e8d72ed):

- `spawn_agent { task_name, agent_type, fork_turns none|all, message | items[], model?, reasoning_effort?, service_tier? }` — "Spawned agents inherit your current model by default. Omit `model` to use that preferred default; set `model` only when an explicit override is needed." "Pick model overrides from the latest `<model_catalog>` listing." The harness validates the child's effort and service tier against the child model. Full-history forks (`fork_turns=all`) inherit the parent agent type.
- `send_input` / `send_message` (`interrupt: true` redirects at once), `followup_task`, `wait_agent` (first of several ids to finish), a mailbox wait, `interrupt_agent`, `close_agent` ("Completed agents remain open and count toward the concurrency limit until closed"), `list_agents`.
- Agent names are paths `/root/task1/task_3`; messages carry `Message Type: NEW_TASK | MESSAGE | FINAL_ANSWER`.

Config (`[agents]`; keys static 0x0e6c33bf; values observed in the TUI `/debug-config` of a sandbox whose user `config.toml` set `default_subagent_model = "gpt-6-luna"` and `default_subagent_reasoning_effort = "low"`, so those two lines show the configured values, not defaults): `enabled` (true), `max_concurrent_threads_per_session` (`<unset>` → "Codex chooses the default", **number not recovered**; legacy alias `max_threads`), `max_depth` (1, V1 only, ignored by V2), `default_subagent_model`, `default_subagent_reasoning_effort`, `interrupt_message` (true), `job_max_runtime_seconds` (agent jobs). Documented: without a configured default the subagent inherits the parent's model; a model without an effort takes the model's default effort; subagents follow the root session's service tier.

Custom agents: TOML files in `~/.codex/agents/` or `<project>/.codex/agents/` with `name`, `description`, `developer_instructions`, `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, `features.*`, `skills.*`, `nickname_candidates`, `config_file`; `sandbox_mode`, `approval_policy`, `model_provider` and `mcp_servers` are not overridable (documented; static `AgentRoleToml` 0x0e75197e). Built-in roles: `default`, `worker` ("execution and production work"), `explorer` ("fast and authoritative", spawn several in parallel) and an `awaiter` (`model_reasoning_effort = "low"`, `background_terminal_max_timeout = 3600000`, static 0x0e9224a7).

Persistence makes attribution exact: each subagent is a thread with its own rollout and its own row in `state_5.sqlite.threads` (`model`, `reasoning_effort`, `tokens_used`, `agent_role`, `agent_nickname`, `agent_path`, `thread_source`, `history_mode`), linked to its parent by `thread_spawn_edges(parent_thread_id, child_thread_id, status)` (static DDL 0x0eb983b1; observed DB). The harness's error enum (static 0x0eaf830a) includes, among its general variants, `AgentLimitReached` (the concurrency cap), `SessionBudgetExceeded`, `ContextWindowExceeded`, `UsageLimitReached`, `RateLimitExceeded` and `FlexUnavailable`. There are also CSV "agent jobs" (`agent_jobs`, `agent_job_items` tables with `input_csv_path`, `assigned_thread_id`, `attempt_count`).

## 5. Hooks

Twelve events, established by the JSON schemas the binary embeds for every event's input and output (23 schemas, 12 inputs and 11 outputs, static 0x0e9c8ed8–0x0e9cf775, extracted to `../evidence/hook-input-output-schemas.json`; the TUI `/hooks` table shows the first eight): `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `SubagentStart`, `SubagentStop`, `UserPromptSubmit`, `Stop`, `Interrupt`. (The `HookEventsToml` enum run at 0x0e9b2476 lists ten of them; `UserPromptSubmit` and `Stop` appear only through their schemas, at 0x0e9ce1c8 and 0x0e9cebf1.) Inputs carry `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `permission_mode` (`default|acceptEdits|plan|dontAsk|bypassPermissions`), `turn_id` ("Codex extension: expose the active turn id"), `agent_id`, `agent_type`, and per event `tool_name`, `tool_input`, `tool_use_id`, `tool_response`, `prompt`, `trigger`, `reason`, `last_assistant_message`, `stop_hook_active`. Outputs: `continue`, `stopReason`, `suppressOutput`, `systemMessage`, `decision`, `reason`, `hookSpecificOutput { permissionDecision allow|deny|ask, permissionDecisionReason, updatedInput, additionalContext, updatedMCPToolOutput }`; the error strings confirm `PreToolUse` accepts `updatedInput` together with `permissionDecision: allow` (static 0x0e9c8ce2). Handlers: `command`, `http`, `async` with `matcher`, `timeout`, `statusMessage`, `additionalContextLimit` (static keys; the documented default is 2,500). Hooks come from `hooks.json` or inline `[hooks]`, must be trusted (`/hooks`, `hooks.state.<hash>.trusted_hash`) or run with `--dangerously-bypass-hook-trust`; the docs add that `SessionEnd` always runs synchronously.

For relay this is the Codex equivalent of the Claude Code mod's `agent.spawn`: a `PreToolUse` hook matching `spawn_agent` can read the budget snapshot and rewrite the spawn's `model`, `reasoning_effort` and `service_tier` through `updatedInput`, or deny it at critical. `SubagentStart`/`SubagentStop` give `agent_type` and `model` for the ledger.

## 6. Sessions, storage and `exec`

`$CODEX_HOME` (observed `codex doctor`, exec run): `config.toml` (layers: packaged defaults, `/etc/codex/config.toml`, user; `-p <profile>` adds `<name>.config.toml`), `auth.json`, `sessions/` and `archived_sessions/` rollouts, `state_5.sqlite`, `thread_history_1.sqlite` (paginated history: `thread_turns(thread_id, turn_id, status, started_at, completed_at, duration_ms, …)`, `thread_items(item_json)`), `goals_1.sqlite`, `queue_1.sqlite`, `memories_1.sqlite`, `logs_2.sqlite`, `models_cache.json`, `shell_snapshots/`, `thread-writer-locks/`. `codex migrate-rollouts` moves legacy rollouts into the paginated history; `threads.history_mode` says which a thread uses. Rollout item types: `session_meta`, `response_item`, `event_msg`, `turn_context`, `compacted`, `token_usage_record`, `world_state`, `inter_agent_communication`, `security_risk_score`, `realtime_item`, `replacement_history`, `mcp_resource_origins` (static 0x0e727727). The memory prompt in the binary describes them: "append-only jsonl: `session_meta.payload.id` identifies the session, `turn_context` marks turn boundaries, `event_msg` is the lightweight status stream, and `response_item` contains actual messages, tool calls, and tool outputs" (static 0x0ea04cab).

`codex exec` (observed help, `../evidence/captures/exec-help.txt`): `--json` prints JSONL events `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.started|updated|completed`, `error` (`thread.started` and `turn.started` observed; the full list and the `usage { input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens }` payload of `turn.completed` are static, 0x0e967814 — no turn completed in the sandbox); `-o/--output-last-message FILE`; `--ephemeral` writes no session files (do not use it for runs you want to calibrate); `--worktree`; `-C`, `-m`, `-c key=value`, `-p`, `-s read-only|workspace-write|danger-full-access`, `--skip-git-repo-check`, `--output-schema`, `--ignore-user-config`, `--dangerously-bypass-hook-trust`; `exec resume <id>|--last` and `exec fork <id>`. Observed retry behaviour without network: five stream reconnects with growing backoff (0.49, 0.67, 1.0, 1.72 s), then "Falling back from WebSockets to HTTPS transport", then unbounded "Reconnecting... waiting for network" (feature `unbounded_connection_retries`); documented defaults `stream_max_retries` 5, `request_max_retries` 4, `stream_idle_timeout_ms` 300000. Transport is the Responses API over WebSocket with HTTPS fallback (`wss://api.openai.com/v1/responses` for API keys, `chatgpt.com/backend-api/codex` for ChatGPT auth), "responses-lite" for the gpt-6 models.

Session commands relay can use instead of its own marathon plumbing: `codex queue --thread <id> --message`, `codex resume`, `codex fork`, `codex agents` (the shared daemon's agent sessions), and thread goals.

## 7. Goals (the built-in marathon)

Feature `goals` is stable and on by default. `/goal [<objective>|clear|edit|pause|resume]` (observed) sets a goal on a thread; `thread_goals(thread_id, goal_id, objective, status, token_budget, tokens_used, time_used_seconds)` with status `active|paused|blocked|usage_limited|budget_limited|complete` (static DDL 0x0eb99bc4); `goals.max_goal_token_budget` caps the budget ("goal token budget N exceeds the maximum allowed goal token budget of M", static 0x0e54b84a); embedded templates `goals/continuation.md`, `goals/budget_limit.md`, `goals/objective_updated.md`; "continue active goal for idle thread" and `thread_goal_continuation_deferrals` (static 0x0e53032e, 0x0e793743); app-server methods `thread/goal/set|get|clear` and notifications `thread/goal/updated|cleared`. In words: an idle thread with an active goal keeps taking turns until the objective is complete, the token budget is spent, or the account is usage-limited; usage-limited goals resume when the window resets. Relay's marathon maps onto a conductor thread with a goal whose token budget comes from the forecast.

## 8. What was not recovered, and how to get it

The default auto-compaction limit and the default subagent concurrency are numbers computed in code, invisible in the string table and not exposed by `config/read` or `/debug-config` (which prints `<unset>`). Both are configurable, which is what relay should do anyway (`model_auto_compact_token_limit`, `agents.max_concurrent_threads_per_session`). To recover them: a logged-in run with one spawn and `RUST_LOG=debug`, or a Ghidra/IDA session on the functions that reference the strings `model_auto_compact_token_limit` (0x0e6c33bf) and `max_concurrent_threads_per_session` (0x0e5677ba) — REA's native providers do this once such an engine is installed; this analysis had objdump and radare2 only.

Window capacities in credits (`Q_j`) are not published anywhere; they are what `relay calibrate` learns first, from one clean interval of readings.
